# 排名故障修复验证

验证日期：2026-09-09。仅修改本地画质助手，Kazumi 源码及已安装网站规则保持只读。

## 本次故障

最近一次《最强王者的第二人生》第 1 集完整检测，共三个网站、十条线路，耗时 542.6 秒。只有同一网站的一条线路取得足够样本，其余有效媒体多停在一至两个对齐位置，因而无法形成跨站排名。

## 已复现的原因与修复

1. 原批量匹配使用 `fps` 滤镜，再以请求网格标记图片时间。滤镜实际选中的视频帧与标签时间不一致，重新精确提帧后变成其他画面。现在保留输入的整数 PTS 与时间基准，参考和候选均按真实时间定位。
2. 部分 HLS 分片未从关键帧开始，直接跳转会丢失解码参考，三个请求时间可能都取到数秒之后的同一帧。现在预卷五秒后在原始时间轴裁切，并检验三个输出帧的时间间隔。真实 baimao 线路 3 的两组故障请求已恢复到请求后一个视频帧以内。
3. sorani 新解析的媒体地址可以读取，同一个地址约 71 秒后返回 HTTP 403。原流程在全部线路探测完后才采样，地址可能在排队期间过期。现在每条线路独立管理媒体会话，超过 25 秒先刷新，遇到 401/403/410 再最多刷新重试一次；刷新后核对时长、分辨率、编码、显示比例、色彩传递函数以及双方已知的帧率、码率。
4. 原参考仅检查第一帧，后续校验却要求三帧均有效；淡出和黑帧会成为所有来源无法通过的参考。现在参考也检查全部三帧，必要时在附近另取一组。
5. 原搜索只保留单帧最佳候选，重复镜头可能遮住真正匹配；粗采样也可能漏过短镜头。现在先做邻近三帧联合匹配，再尝试有限的粗细搜索，必要时增加一次错相采样。单帧最大距离 0.12、三帧平均距离 0.08 均保留。
6. 排名原来取全部合格来源的样本位置交集，某条缺帧线路可能拖掉其他可比较网站。现在按网站覆盖数、有效线路数、共同位置数依次选择比较组，不根据分数或分辨率挑选。仅缺第四个位置、已有三个共同位置的合格线路会得到保留；全体支持四个位置时仍用四个。
7. 相同媒体的缓存复用还要核对初始规格；原会话已经刷新过时，重复线路使用自身会话独立取样，避免把旧地址对应关系延用到刷新后的媒体。

## 验证证据

同一组真实 moonci 线路 2 与 baimao 线路 3 对齐复测：原来 109.92 秒、2/4 个位置通过；修复后 32.84 秒、4/4 个位置全部直接通过。该计时只包含对齐，不包含参考取样、模型加载或评分。

同一标题、集数、三个网站和十条线路的完整公网复测耗时 465.4 秒，恢复三个网站的排名。sorani、moonci 三条线路、baimao 的 1/3/4 线路都取得四个共同位置；baimao 线路 6 取得三个位置，线路 2/5 仍未提供可解析媒体。本次比最近失败记录少用 77.2 秒，但参考源选择和网络响应也有变化，不能将差值视为受控基准。

完整复测还暴露出三位置的 720p 线路被四位置比较组排除的问题，随后用相同数据结构的回归修正了比较组优先级。最后补充的刷新规格、缓存及比较组防线由本地集成测试验证；完整公网复测没有重复运行。这次没有因为该线路分辨率低而跳过它的取样与评分。

本地生成视频的回归覆盖 24 fps、23.976 fps、变帧率、301.4396 秒起点及非关键帧 HLS。快速切镜头素材分别增加七帧和约五秒片头，验证能够在原阈值下找回相同内容。其他回归覆盖过期地址、取消、刷新后版本改变、共同位置不一致及无效模型分数。

最终 Python 全量测试 137 项通过（49.124 秒），前端契约检查和诊断汇总脚本 5 项自测通过。另完成 UTF-8 和 Git 差异检查。

逐位置诊断增加真实参考时间、候选时间、匹配距离及匹配方法；刷新次数及耗时一并记录。长期诊断不保存媒体地址、图片路径、Cookie 或签名。原始调查文件和公网复测结果仅保存在被 Git 忽略的 `data/`。

## 保留的边界

至少两个网站、至少三个共同正文位置才能生成排名。缺少可用媒体或不同版本仍明确显示未参与排名；低分辨率、高码率以及缺失码率的来源不会因规格被淘汰。公网耗时会随源站响应和当前机器负载变化，单次计时不代表固定加速比例。
